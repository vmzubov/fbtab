# fbtab

Выполняет `SELECT` из sql-файлов в Firebird и пишет настоящий tsv: одна строка файла — одна строка
результата, NULL отличается от пустой строки, формат не зависит от региональных настроек.

English: [README.md](README.md).

```
fbtab --db server:alias --user REPORTS --out results  01_clients.sql 02_payments.sql
OK 01_clients rows=184203 sec=2.1
OK 02_payments rows=5120377 sec=48.9
```

## Зачем

Вывод `isql` рассчитан на чтение глазами: колонки выровнены пробелами или идут столбиком, NULL
выглядит как текст, перевод строки внутри значения ломает строку, числа и даты — в формате isql.
Чтобы превратить это в данные для pandas, DuckDB или таблицы, под каждый запрос нужен свой разбор.
fbtab пишет файл, который эти инструменты читают как есть.

## Что делает

- **Только чтение.** Каждый sql-файл выполняется в своём соединении, в транзакции `READ ONLY`, в
  конце — rollback. Принимаются только `SELECT`, `WITH`, `EXECUTE BLOCK` и `EXECUTE PROCEDURE`; файл
  с чем-то ещё отклоняется до подключения к базе.
- **Скрипты для isql работают без правок.** `SET TERM` понимается; `SET LIST`, `SET COUNT`,
  `SET HEADING` и другие настройки вывода пропускаются.
- **Все запросы файла готовятся (prepare) до выполнения первого**: опечатка в последнем запросе
  видна сразу, а не через час.
- **Поток.** Строки идут с сервера в файл по одной, размер результата не важен.
- **Нет недописанных результатов.** Данные пишутся в `<имя>.tsv.part`, файл получает имя
  `<имя>.tsv` только когда запрос дочитан.
- **Подключается туда же, куда isql.** По умолчанию — через `fbclient`, поэтому работают все плагины
  аутентификации, шифрование и сжатие канала, которые работают у `isql`. Ключ `--managed` — без
  fbclient (только Srp и Legacy_Auth).
- **Пароль не передаётся в командной строке и нигде не хранится**: берётся из `FBTAB_PASSWORD` или
  `ISC_PASSWORD` либо вводится с клавиатуры.

Firebird 3, 4 и 5 (тесты идут на 5). Windows и Linux, x64.

## Запуск

```
fbtab --db <база> --user <пользователь> [ключи] <файл.sql> [<файл.sql> ...]

  --db <база>            host:alias, host/port:path, inet://host:port/path или локальный путь
  --user <пользователь>  имя пользователя (по умолчанию ISC_USER)
  --role <роль>          роль
  --charset <имя>        кодировка соединения (по умолчанию UTF8)
  --fbclient <путь>      библиотека fbclient (по умолчанию FBTAB_FBCLIENT, затем рядом с fbtab,
                         затем та, что найдёт система)
  --managed              подключаться без fbclient
  --isolation <режим>    read-committed (по умолчанию) или snapshot
  --out <папка>          куда писать (по умолчанию текущая папка)
  --version, --help
```

В стандартный вывод идёт по одной строке на sql-файл, ход выполнения — в поток ошибок:

```
OK <имя> rows=<n> sec=<s>
ERROR <имя> <sqlstate или -> <сообщение>
CANCELLED <имя> rows=<n> sec=<s>
```

| Код выхода | Что значит |
|---|---|
| 0 | все файлы выгружены |
| 1 | хотя бы один файл с ошибкой (плохой sql, запрещённый оператор); остальные файлы выполнены |
| 2 | нет связи или неверные имя и пароль; прогон останавливается на этом файле |
| 3 | неверные аргументы, нет файла, нет пароля, не загрузился fbclient |
| 4 | прервано Ctrl+C: запрос отменяется на сервере, транзакция откатывается |

### Изоляция

По умолчанию `READ COMMITTED READ ONLY`: долгая выгрузка не держит сборку мусора на нагруженном
сервере, но два запроса одного файла могут видеть чуть разные моменты. Когда им нужен один момент,
напишите в первых строках-комментариях файла (или передайте `--isolation snapshot`):

```sql
-- isolation: snapshot
select ...;
select ...;
```

## Результат

Для `report.sql` получаются `report.tsv` и `report.meta.json`. Второй и третий запросы того же файла
дают `report_2.tsv`, `report_3.tsv`, у каждого свой `.meta.json`.

### tsv

UTF-8 без BOM, конец строки LF, первая строка — имена колонок, разделитель — таб. Внутри значения:

| В данных | В файле |
|---|---|
| NULL | `\N` |
| пустая строка | пусто |
| обратная косая черта | `\\` |
| таб | `\t` |
| перевод строки | `\n` |
| возврат каретки | `\r` |

Это текстовый формат PostgreSQL `COPY`. Строка файла — всегда ровно одна строка результата, поэтому
на нём работают `wc -l`, `grep`, `awk` и `split`.

| Тип Firebird | Как пишется |
|---|---|
| SMALLINT, INTEGER, BIGINT, INT128 | цифры |
| NUMERIC, DECIMAL | точно, с точкой и всеми знаками масштаба: `12.50` |
| DOUBLE PRECISION, FLOAT | кратчайшая запись, которая читается обратно в то же число: `0.1`, `1E+300` |
| DECFLOAT | обычное число: `1.5` |
| DATE | `2026-11-22` |
| TIME | `09:10:00.1234` |
| TIMESTAMP | `2026-11-22 09:10:00.1234` |
| TIME / TIMESTAMP WITH TIME ZONE | то же и зона, как она хранится: `2026-11-22 10:00:00.1234 Europe/Budapest`, `10:00:00.0000 +03:00` |
| BOOLEAN | `true` / `false` |
| CHAR(n) | без хвостовых пробелов, которыми Firebird дополняет значение |
| VARCHAR, BLOB SUB_TYPE TEXT | текст |
| двоичный BLOB, CHARACTER SET OCTETS | hex: `0x0001FF` |

### Как читать

DuckDB:

```sql
select * from read_csv('report.tsv', delim = '\t', header = true, nullstr = '\N', quote = '', escape = '');
```

pandas:

```python
import csv, pandas as pd
df = pd.read_csv('report.tsv', sep='\t', na_values=['\\N'], keep_default_na=False, quoting=csv.QUOTE_NONE)
```

DuckDB угадывает типы колонок по значениям и принимает hex вида `0x0001FF` за число: для двоичных
колонок добавьте `types = {'BIN': 'VARCHAR'}` (или `all_varchar = true`). В pandas то же делает
`dtype=str`.

Оба оставляют `\t`, `\n`, `\r` и `\\` внутри текста как записано. Если в текстах бывают табы,
переводы строк или обратная косая черта, раскройте такие колонки:

```python
import re
unescape = lambda s: re.sub(r'\\(.)', lambda m: {'t': '\t', 'n': '\n', 'r': '\r'}.get(m[1], m[1]), s)
```

### meta.json

Что выполнено и что получено: текст запроса и номер его строки в файле, число строк, время начала
и конца, время сервера, версия движка, пользователь, изоляция; по каждой колонке — имя, тип
Firebird, длина, масштаб и допускает ли NULL.

## Что защищает базу

1. Транзакция `READ ONLY`: Firebird сам не даст выполнить в ней `INSERT`, `UPDATE`, `DELETE` и DDL,
   в том числе внутри `EXECUTE BLOCK` и в процедурах, которые вызывает запрос.
2. Операторы проверяются по первым словам до отправки на сервер: скрипт с `UPDATE` или `COMMIT`
   не доходит даже до подключения.

Единственное, что транзакция только на чтение разрешает, — запись во временные таблицы (GTT)
`ON COMMIT DELETE ROWS`; такие строки живут до конца транзакции, а её fbtab откатывает.

## Ограничения

- Параметров нет: sql выполняется как написан.
- NUMERIC длиннее 28 значащих цифр драйвер не читает в .NET decimal.
- Через fbclient выражение, тип которого — строка нулевой длины и которое может быть NULL (например
  `nullif('', X)`), пишется как `\N` в обоих случаях: драйвер их не различает. Обычный `''` и
  настоящие колонки это не затрагивает.
- Вывод в CSV и Parquet запланирован, не сделан.

## Сборка

Нужен .NET 10 SDK.

```sh
dotnet build
dotnet test
scripts/publish.sh     # out/win-x64/fbtab.exe и out/linux-x64/fbtab: один файл, .NET не нужен
```

Без переменных ниже `dotnet test` выполняет юнит-тесты и пропускает те, которым нужен сервер.

| Переменная | Для чего |
|---|---|
| `FBTAB_TEST_DB` | база, которую тесты создают и наполняют, например `localhost/3055:/tmp/fbtab_test.fdb` (Firebird 4+) |
| `FBTAB_TEST_USER`, `FBTAB_TEST_PASSWORD` | по умолчанию `SYSDBA` / `masterkey` |
| `FBTAB_TEST_FBCLIENT` | путь к fbclient — для тестов, которые подключаются через него |

fbclient в состав fbtab не входит: возьмите `fbclient.dll` (64-бит) и нужные ему файлы из своей
установки Firebird или из zip-комплекта Firebird и положите рядом с `fbtab.exe` либо укажите путь
ключом `--fbclient`.
